Updates and rollback

How updates and rollback work

HarborBuddy updates a container only when the image behind its reference has a new image ID. It keeps the original container as a stopped backup until the replacement is ready, and puts the original back if the replacement fails.

How a new image is detected

Each cycle, HarborBuddy pulls the exact image reference stored in each eligible container, such as nginx:1.27, and compares the pulled image ID with the image ID the container runs. A changed tag alone is not enough: the image itself must differ. Identical references are pulled once per cycle, and pulls run concurrently.

The replacement, step by step

  1. Pull the image reference stored in the container configuration.
  2. Compare the pulled image ID with the running image ID.
  3. Re-inspect the container to make sure it did not change during the cycle.
  4. Back up the original: rename it to <name>-harborbuddy-backup-<n> (the name records its restart policy), disable the restart policy temporarily, stop it, and disconnect its networks.
  5. Create the replacement with the original name, host configuration, reusable mounts, and network attachments. Settings that came from the old image, such as its ENV entries, labels, command, and health check, are dropped so the new image's defaults apply. Values you set yourself are kept.
  6. Start and wait for Docker to report the replacement healthy, or for two seconds of process stability when the image has no health check.
  7. Remove the backup once the replacement is ready.

The old container stops before the new one starts, so each update causes a brief interruption. HarborBuddy is not a rolling or zero-downtime updater.

What happens when an update fails

If creation, startup, or the readiness check fails, HarborBuddy removes the failed replacement, restores the original container's name, networks, and restart policy, and starts it again. The failed image is remembered: HarborBuddy reports previously_failed and does not retry that image for that container until a different image is published or HarborBuddy restarts.

Rollback is best-effort. Docker or the host can also fail during recovery, so keep backups of stateful data and opt migration-sensitive services out of unattended updates.

Keep a known-good image

Set updates.rollback_image_retention (or HARBORBUDDY_ROLLBACK_IMAGE_RETENTION) to keep that many previous working images per image reference, tagged as localhost/harborbuddy-rollback/<sha256>:<slot>. That lets you roll back by hand later, even after the registry tag moved on. The default is 0.

Shutdown and crash recovery

On SIGTERM, HarborBuddy starts no new replacements but finishes, or rolls back, the one in progress. Give it time to do that with stop_grace_period: 2m in Compose; Docker's default of 10 seconds can cut a transaction short.

If HarborBuddy is killed anyway, the original can be left as a stopped backup. At the start of each cycle HarborBuddy looks for backups from the last 48 hours whose original name is free, renames them back, restores the recorded restart policy, reconnects the primary network, and starts them. Older backups and backups whose name is taken are only logged.

Following an update in the logs

Every update logs stable event names with container, image, transaction, failure, and rollback fields. All work in one scheduled run shares a cycle_id. Set HARBORBUDDY_LOG_JSON=true to ship logs to a collector, or send SIGUSR1 to switch to debug logging temporarily.
