For standalone Docker Engine

Automatic Docker updates with a rollback path.

HarborBuddy checks the image references your containers already use. When an image ID changes, it recreates the container from Docker's inspection data and keeps the stopped original as a backup until the replacement is ready.

The update route

Pull the image. Compare IDs. Replace only when something changed.

01

Discover eligible containers

Allow and deny filters, per-container labels, and recreation checks narrow the run to containers HarborBuddy can support.

02

Pull and confirm the image

HarborBuddy pulls each configured reference and compares immutable image IDs. An unchanged ID means no replacement.

03

Replace, check, or roll back

The old container becomes a temporary backup while the replacement starts. If readiness fails, HarborBuddy attempts to restore and restart it.

Controls for unattended runs

Checks before an automatic restart.

HarborBuddy re-inspects before changing anything, retains operator-supplied settings while allowing new image defaults to take effect, and reports configurations it cannot reproduce.

Maintenance

Dangling images by default. More only when asked.

Cleanup deletes dangling images older than 24 hours by default. Stopped containers, unused tagged images, local networks, volumes, and build cache each require an explicit opt-in.

Observability

Logs you can follow across a cycle

Stable event names and cycle IDs connect startup configuration, update transactions, rollback outcomes, cleanup summaries, warnings, and failures. Routine skips stay at debug.

Self-update

Self-update uses the same backup plan

A short-lived helper takes over after HarborBuddy exits, recreates the daemon, checks startup, and attempts to restore the backup if the handoff fails.

!

Before you install

Docker control is host control.

HarborBuddy needs read/write access to the Docker API to pull images and create, stop, rename, start, and remove containers. Treat the Docker socket as host-level administrative access, and run only one active HarborBuddy controller per daemon. Updates cause a brief interruption, rollback is best-effort, and authenticated private-registry pulls are not currently supported. Without a Docker health check, readiness means only that the process stayed running for two seconds.

A good fit

You run a standalone Docker host

  • You want scheduled updates with readiness checks and an attempted rollback path.
  • Your running containers can be recreated from Docker's inspection data.
  • You want filters, dry runs, and structured logs for operational control.

Not supported

Some workloads are intentionally skipped

  • Docker Swarm task containers
  • Auto-remove containers
  • Containers sharing another container's network, PID, IPC, or UTS namespace
  • Containers with mounts HarborBuddy cannot reproduce

Common questions

What changes, what gets checked, and what gets skipped.

How does HarborBuddy decide a container needs an update?

HarborBuddy pulls the container's configured image reference and compares the pulled image ID with the image ID currently running. A changed tag alone is not enough; the underlying image ID must differ.

What does ready mean without a health check?

HarborBuddy checks that the replacement process stays running without restarting for two seconds. That is a process-stability check, not proof that the application is healthy, so define a Docker health check when application readiness matters.

Does an update cause downtime?

Yes. HarborBuddy stops the old container before starting its replacement, so updates cause a brief interruption. It is not a rolling or zero-downtime updater.

What happens when a replacement container fails to start?

HarborBuddy attempts to remove the failed replacement, restore the prior container's name, networks, and restart policy, and start it again. Rollback is best-effort because Docker or the host can also fail during recovery.

Can HarborBuddy retain a known-working image for rollback?

Yes. Set updates.rollback_image_retention or HARBORBUDDY_ROLLBACK_IMAGE_RETENTION to the number of prior successful images to keep per full image reference. The opt-in default is 0. Retention runs after readiness, uses isolated deterministic local tags, never deliberately removes images used by running or stopped containers, and reports maintenance failures as warnings without failing a successful update.

Can HarborBuddy update itself?

Yes. Automatic self-update is enabled by default and uses a short-lived helper container to replace the HarborBuddy daemon after it exits. It can be disabled independently when manual change control is preferred.

Does dry-run mode change running containers?

No. Dry-run mode pulls eligible image references and updates the Docker Engine's local image cache so it can report real image-ID differences, but it never stops, recreates, renames, or removes containers and does not remove or prune any cleanup resource.

Can HarborBuddy clean all unused Docker resources?

Yes, when explicitly enabled. By default, cleanup deletes dangling images older than 24 hours. HARBORBUDDY_CLEANUP_ALL=true also enables stopped containers, unused tagged images, unused local networks, unused volumes, and unused build cache. For containers, networks, and volumes, age means time since creation, not time since becoming unused. Each broader category has its own switch and defaults to off. Preview the exact candidates with dry-run first; unused-volume cleanup can permanently remove application data.

Does HarborBuddy support Docker Swarm?

No. HarborBuddy targets standalone Docker Engine hosts. It skips Swarm tasks, auto-remove containers, container namespace dependencies, and inspected mounts it cannot reproduce.

What access does HarborBuddy need?

HarborBuddy needs read/write access to the Docker API so it can pull images and create, stop, rename, start, and remove containers. Docker daemon access should be treated as equivalent to host-level administrative access.
