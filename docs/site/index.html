For standalone Docker Engine

Container updates with a safe way back.

HarborBuddy watches the image references you already run, replaces a container only when its image ID changes, and keeps the previous container ready until the new one proves healthy.

The update route

Pull. Compare. Replace only when the route is clear.

01

Discover eligible containers

Allow and deny filters, per-container labels, and recreation checks narrow the run to containers HarborBuddy can manage safely.

02

Pull and confirm the image

HarborBuddy pulls each configured reference and compares immutable image IDs. An unchanged ID means no replacement.

03

Replace, verify, or roll back

The original becomes a temporary backup while the replacement starts. Failed readiness restores the prior name, networks, and container.

Designed for unattended runs

The boring parts are the feature.

HarborBuddy is deliberately conservative around replacement. It re-inspects before mutation, carries the original configuration forward, and reports cases it cannot handle instead of improvising.

Self-update

Even the updater gets a rollback path

A short-lived helper takes over after HarborBuddy exits, recreates the daemon, verifies startup, and restores the backup if the handoff fails.

!

Know the access boundary

Docker control is host control.

HarborBuddy needs read/write access to the Docker API to pull images and create, stop, rename, start, and remove containers. Treat the Docker socket as host-level administrative access, and run only one active HarborBuddy controller per daemon.

A good fit

You run a standalone Docker host

  • You want scheduled updates without giving up readiness checks and rollback.
  • Your containers can be recreated from their inspected Docker configuration.
  • You want filters, dry runs, and structured logs for operational control.

Outside the lane

Some workloads are intentionally skipped

  • Docker Swarm task containers
  • Auto-remove containers
  • Containers sharing another container's network namespace

Common questions

What HarborBuddy changes—and what it refuses to guess.

How does HarborBuddy decide a container needs an update?

HarborBuddy pulls the container's configured image reference and compares the pulled image ID with the image ID currently running. A changed tag alone is not enough; the underlying image ID must differ.

What happens when a replacement container fails to start?

HarborBuddy removes the failed replacement, restores the prior container's name and networks, and restarts it. The old container remains available as a temporary backup until the replacement passes readiness checks.

Can HarborBuddy update itself?

Yes. Automatic self-update is enabled by default and uses a short-lived helper container to replace the HarborBuddy daemon after it exits. It can be disabled independently when manual change control is preferred.

Does dry-run mode change running containers?

No. Dry-run mode pulls eligible image references and updates the Docker Engine's local image cache so it can report real image-ID differences, but it never stops, recreates, renames, or removes containers and does not delete images.

Does HarborBuddy support Docker Swarm?

No. HarborBuddy targets standalone Docker Engine hosts. Swarm task containers and containers that cannot be safely recreated are skipped.

What access does HarborBuddy need?

HarborBuddy needs read/write access to the Docker API so it can pull images and create, stop, rename, start, and remove containers. Docker daemon access should be treated as equivalent to host-level administrative access.
